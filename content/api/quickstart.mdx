Use this guide to verify that `space` (the Space API) is reachable, discover the space
instead of hardcoding its paths, and send one streamed chat turn.

## Before you start

You need a running XO Space. The API runs inside it on port `5002` by
default.

```bash
export BASE="http://localhost:5002"
```

Local desktop requests use loopback and do not need an auth header. A remote
space proxy can require a host-provided `Authorization: Bearer <token>` or
`Coder-Session-Token: <token>` header. Add one only when that space host tells
you to: the FastAPI app itself does not validate either header. That space
proxy token is different from the upstream swarm token described in the [API
overview](/api-reference/overview#auth-model).

<Steps>
  <Step>
    ### Verify the API process

    ```bash
    curl --fail --silent --show-error "$BASE/"
    ```

    A healthy instance returns:

    ```json
    { "status": "Space API running" }
    ```

    If this request cannot connect, confirm that the Space daemon is running
    and that `BASE` points to its current local port or tunnel URL.
  </Step>

  <Step>
    ### Discover the space

    ```bash
    curl --fail --silent --show-error "$BASE/api/config/workspace"
    ```

    The response identifies the active backend and its canonical projects root:

    ```json
    {
      "roots": {
        "openclaw": "/Users/me/xo-projects",
        "claude_code": "/Users/me/xo-projects"
      },
      "default": "openclaw"
    }
    ```

    Use `roots[default]` whenever your client creates or opens a project. Do not
    hardcode `~/xo-projects/`; the server can override it with
    `XO_PROJECTS_ROOT`.
  </Step>

  <Step>
    ### Reserve a first chat stream

    ```bash
    curl --fail --silent --show-error \
      -X POST "$BASE/api/chat/prompt" \
      -H "Content-Type: application/json" \
      -d '{"text":"Reply with exactly: Space API connected."}'
    ```

    The API returns a stream identifier and a logical session identifier:

    ```json
    {
      "stream_id": "8f3a2b1c-...",
      "session_id": "9d4e5f6a-..."
    }
    ```

    Copy `stream_id` for the next step. On a new OpenClaw session,
    `session_id` can initially be `null`; the stream will emit the real id in a
    `session-created` event.
  </Step>

  <Step>
    ### Consume the streamed response

    Replace `<stream_id>` with the value returned above:

    ```bash
    curl --no-buffer "$BASE/api/chat/stream/<stream_id>"
    ```

    A normal new-session turn follows this shape:

    ```text
    event: session-created
    data: {"session_id":"9d4e5f6a-..."}

    event: text-delta
    data: {"session_id":"9d4e5f6a-...","text":"Space API connected."}

    event: done
    data: {"finish_reason":"stop","session_id":"9d4e5f6a-..."}
    ```

    Accumulate every `text-delta`, ignore `heartbeat` content, and stop on `done`
    or `agent-error`. Calling `prompt` without opening its stream leaves an
    in-memory entry behind, so clients should always consume or explicitly abort a
    reserved stream.
  </Step>
</Steps>

<Callout type="info">
The status and space-config requests work before you build a chat UI. A chat
turn also requires a configured runtime and model provider. Use the [Auth
API](/api-reference/auth-api) for Clerk and Claude/Codex bootstrap flows, and
`GET /api/models` from the [Config API](/api-reference/config-api) to populate
the model choices your space exposes.
</Callout>

## Confirm the integration

Before moving on, verify all four outcomes:

- `/` returns HTTP `200` with `{ "status": "Space API running" }`.
- `/api/config/workspace` returns a `default` key present in `roots`.
- `/api/chat/prompt` returns a non-empty `stream_id`.
- The SSE request ends with `done`, or surfaces an actionable `agent-error`.
