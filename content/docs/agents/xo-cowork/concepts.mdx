## Workspace

Your workspace is the folder set by `XO_PROJECTS_ROOT`. Cowork has exactly one **Workspace chat**, whose coordinator works in that folder and sees every project. Write to the Workspace when you don't know, or don't care, which project should take a request. It answers, forwards the work, or proposes a new project.

## Project

Every direct, non-hidden sub-folder of the workspace is a project, and each one gets its own **project chat** and coordinator. The chat is created the first time the project is listed. When a project appears later, the Workspace timeline gets a note such as "Project billing-api created."

A project's `.xo/` folder belongs to XO Space. It holds its identity (`project.json`), todos, work items, peers, and the `worktrees/` folder for threads. `.xo/` is committed with your code, except `worktrees/`. Agents may read `.xo/` but never write it.

**Create XO Project** in the Cowork UI scaffolds exactly two things: `.xo/` and a short `AGENTS.md`:

```md
# AGENTS.md

This folder is an XO Space project. For any agent working here:

- `.xo/` belongs to XO Space (identity, todos, work items, peers). Read it if useful; never edit it, except to resolve git conflict markers in a `.xo/` file.
- Record the project's todos through XO Space, not only in a native todo tool, which nobody else sees.
- Keep your work inside this folder.
```

Add your project's own instructions below that: how to build, test and run it, and what an agent wouldn't guess.

## Coordinator

A coordinator is the agent that speaks for a chat. There is one for the Workspace and one for each project. Coordinators are **read-only**:

- **They can:** read, search and list files, run `git log`, `git show` and `ls`, and use XO's own messaging tools.
- **They can't:** edit, create or delete files, fetch from the web, search the web, create worktrees, or schedule work. XO enforces this in policy, not only in the prompt.

Any change to a repository goes to a thread. A coordinator ends each of its turns by replying, forwarding or starting a thread, never with silent text. A coordinator is replaced by a fresh one every 30 inputs or 24 hours, handing over its memory and open work. See [How messages travel](/docs/agents/xo-cowork/how-messages-travel).

## Thread

A thread is one task with its own agent. It starts from a message on a project's timeline. It runs in its own git checkout at `<project>/.xo/worktrees/thread-<ts>`, on a branch named `xo/thread-` plus six hex characters. If the project isn't a git repository, the thread works in the project folder itself and is told so.

A thread keeps a checklist, using `○` to do, `✱` in progress and `✓` done, and it replies to you in the thread. It asks you before anything destructive. Its agent is fixed for its whole life, but you can change its model and effort.

| Stored state | Meaning | The UI shows |
|---|---|---|
| `working` | Its agent is on it, or waiting for its coordinator | **Working** while the session is busy, **Idle** when it has gone quiet |
| `needs_reply` | It replied with steps left, or its last turn was stopped | **Needs you** (reply in words), or **Stopped** after a stop |
| `needs_approval` | A permission, question or blocking ask is open | **Needs you** |
| `done` | It replied and every checklist step is ✓ | **Done** |
| `failed` | Its input failed, or it ended without replying | **Stopped** |
| `paused` | XO paused it after repeated denied actions | **Paused** |
| `resolved` | You or an agent marked it finished | **Resolved** |

A new message reopens a resolved or paused thread. See [Threads](/docs/agents/xo-cowork/using-cowork/threads).

## Chat (plain chat)

Under **Chats** you talk to one agent in one folder, outside the coordinators. A plain chat has no system prompt and no reply gate, so the CLI's own answer is the reply. You choose its folder, agent, model, effort and what it may do. "Bypass" is never offered. See [Chats](/docs/agents/xo-cowork/using-cowork/chats).

## Card

A card is a thread's one-line status. XO computes it from rules after each input, never from the agent's own claim. It holds a state, a headline, what happened, and what the thread needs from you. Cards drive the thread chips and the **Now** strip in the UI.

## Hop

A hop is one recorded hand-off between layers: the Workspace forwarding to a project, a coordinator briefing a thread, or a thread reporting back. There are six kinds: `forward`, `relay`, `brief`, `ask`, `status` and `answer`. A hop moves from `sent` to `delivered` to `answered`. Turn on **Show how messages travel** in Settings to see hops as quiet lines inside threads.

## Review item ("Needs you")

A review item is anything that waits on you:

- a permission for an action;
- a question;
- an approval of a plan or a risky step;
- an action only you can take;
- a proposed project or job;
- a usage-limit choice;
- an integrity warning;
- a suggestion to pause a stuck thread.

Its risk is computed by XO's policy, never claimed by the agent. Items are listed most destructive first, then blocking, then oldest. Each item can be decided once, and only by you. See [Home and decisions](/docs/agents/xo-cowork/using-cowork/home-and-decisions).

## Rule

A rule lets agents do one thing without asking. Only you make rules, from a decision (**Make it a rule**), and the rule's sentence is shown to you word for word. XO also ships a few safe default rules, such as reading inside the project and read-only git, and you can revoke any of them. See [Permissions and rules](/docs/agents/xo-cowork/permissions-and-rules).

## Worktree

A worktree is a thread's own git checkout. XO removes one by itself only when nothing would be lost, a week after the thread was resolved. You can remove one sooner from **Settings → Worktrees**, and XO shows exactly what would go first. See [Worktrees](/docs/agents/xo-cowork/worktrees).

## Memory

Each coordinator keeps markdown memory files: an index, `MEMORY.md`, plus one file per memory. They live in XO's state folder, not in your project. Coordinators write memory; threads can read their project's. Memory refuses anything that looks like a secret. See [Memory and jobs](/docs/agents/xo-cowork/memory-and-jobs).

## Session, turn, input and run

These are the engine's terms. They appear in the API and in the UI's activity views.

- **Session:** one agent conversation, on one agent for life. Every coordinator, thread and chat has one.
- **Turn:** one answer from the CLI. It ends as finished, failed, stopped or interrupted.
- **Input:** what the agent works on from a message until it goes idle. One input can take several turns.
- **Run:** a sub-agent or background task inside a session. Runs form a tree you can open, read and stop.

An idle agent process is kept for 10 minutes, then released and resumed later from its saved conversation. See [The storm engine](/docs/agents/xo-cowork/engine).

## Pool

A pool is one agent account, such as your Claude login. Its state decides what may start:

| State | What may start |
|---|---|
| `open` | Everything |
| `warn` | Urgent work only. A window is at least 80% used. |
| `closed` | Nothing, until the reset. A usage limit was reached. |
| `paid` | Nothing, until you choose. The account moved onto paid extra usage. |

Turns already running always finish. Cowork shows a closed or paid pool as a line above the composer, such as **Paused until 14:00 · usage limit · running work finishes, new work waits**.

## Job

A job is a scheduled agent run. Each time it fires, it opens a new thread in a project. An agent can propose a job, but nothing is scheduled until you allow it. A job never runs again while its previous run is still working. See [Memory and jobs](/docs/agents/xo-cowork/memory-and-jobs).
